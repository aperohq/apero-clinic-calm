## What platform backups cover and omit

A recoverable full Supabase database backup includes database state and Auth records/password hashes. It does not restore Edge code, deployment assets, Auth dashboard settings, project/API keys, external secrets, provider assets or Storage bytes. Auth schema restoration must be version compatible; user hashes can preserve password login, but working password/MFA/SSO/passkey/session recovery is **not tested here**. New JWT/API signing keys may invalidate sessions; deliberately require reauthentication after incident recovery, preserve user UUID/profile links and restore Auth settings/providers/redirect allowlists/SMTP separately. Never email shared replacement passwords.

Physical backups are not directly downloadable as logical archives. Supabase documents daily backups on eligible paid plans and plan-specific windows; those windows are **not verified for this project**. Supabase-managed restores cause downtime. Project deletion deletes its managed backups, so vendor-managed isolation is insufficient for operator/account/project loss. Downloaded role backups omit custom DB role passwords; reset these separately. [Supabase backup capabilities](https://supabase.com/docs/guides/platform/backups).

A managed clone copies Auth hashes and database state but needs project configuration/storage/code reapplication; physical clones can start external database jobs immediately. Prefer a network-isolated logical drill when containment is required. [Supabase clone limitations](https://supabase.com/docs/guides/platform/clone-project).

## Backup access and revocation

Only named Apero platform/recovery operators and designated key custodians may access backups; ordinary clinic users, clinic Owners/Managers/Staff and dashboard support roles have no download/decrypt permission. A full backup bypasses tenant boundaries and exposes historical patient/Auth records, so dashboard permission never implies backup permission. Human access uses individual MFA accounts; automated writer uses dedicated workload identity, with public age recipients only. Recovery private keys stay off the production host and routine writer. Audit every recovery read/decryption and review access quarterly.

On departure/compromise revoke individual provider/Git/Lovable/Supabase sessions/tokens and bucket IAM access, remove runner credentials, rotate DB/workspace secrets if exposed, and replace future encryption recipients. Keep revoked-era decryption keys under two-person custody until their retained ciphertext expires; rotating a recipient alone does not revoke access to old downloaded ciphertext. Do not share passwords, and do not let a single production compromise delete backups and their key escrow.

## Selected architecture and schedule

Design selected; automation/storage not activated.

1. **Platform:** verify paid daily managed backups; recommended 7-day PITR once approved/enabled. PITR replaces daily backup mode, rather than two independent layers. Review available recovery points at opening daily and before any destructive migration.
2. **Independent:** hourly complete logical DB+Auth/history/schema archive and password-free role catalog, encrypted before writing. User-approved GitHub hosted runner, PostgreSQL 17 clients and age, outside the production project. The committed workflow uses read-only DB sessions, temporary key/credential files in tmpfs, disabled swap/core dumps and no GitHub backup artifacts.
3. **Configuration:** encrypted current+published Retell agent/flow/KB metadata each night **and before/after every publish**; preserve approved original KB/voice assets. Platform settings snapshot before changes; weekly encrypted Git mirror/bundle. Source release hashes and exported config hashes accompany the bundle. Configuration backups containing operational credentials require the same restrictive custody.

**Retention (implemented in the reviewed S3 template; not yet provisioned):** hourly restore points for 48 hours; one daily point for 35 days; one Sunday weekly point for 12 weeks; one first-of-month point for 12 months. Promote/reference a verified complete set atomically, not by moving/deleting the only good copy. Configuration/code sets: daily 35 days, weekly 12 weeks, monthly 12 months and before each change under the same expiry. No indefinite backup retention. Hold an incident-selected backup only with a named owner, documented reason and review/expiry date. This is backup retention, not patient-record retention.

Lifecycle deletes expired objects and expired **noncurrent versions**, incomplete uploads, local ciphertext staging after confirmed upload/read-back, and disposable recovered environments after validation/incident closure. Never expire the last usable recovery set while replacements are failing; open a critical incident and explicitly extend that set with an expiry. S3 prefixes hourly/daily/weekly/monthly use 2/35/84/366-day lifecycle and matching initial Governance locks. Noncurrent versions expire after one day noncurrent only when their original lock has expired; expired delete markers/incomplete multipart uploads are cleaned. UTC rounding/asynchronous deletion can retain longer, never less than policy.

## Repeatable database backup

Install supported PostgreSQL 17 `pg_dump`, `pg_dumpall`, `pg_restore`, `psql`, plus age. Pin tested versions in the runner image. Provide trusted TLS root certificate and secret-managed libpq settings. Use a 0700 directory outside the repository and encrypted host volume. Disable shell tracing, core dumps and swap/plaintext temp files on a host handling restored data. Scheduler must enforce a timeout (initially 45 minutes), mutual exclusion and noninteractive execution.

```bash
# Load libpq values from the secret manager; never paste a password here.
# PGPASSFILE must be 0600, output directory 0700; PGSSLMODE=verify-full.
export BACKUP_DESTINATION_APPROVED=yes
python3 scripts/operations/database_backup.py create \
  --destination /approved/encrypted-volume/apero/database-backups \
  --recipients /approved/config/backup-recipients.txt
# On the isolated verification runner/custodian host:
python3 scripts/operations/database_backup.py verify \
  --bundle /approved/encrypted-volume/apero/database-backups/SELECTED_BUNDLE \
  --identity /approved/secrets/backup-age-identity.txt
```

The archive captures `public`, `auth`, `storage`, `supabase_migrations`, `extensions` in one pg_dump transaction; keeps owner/ACL/default privileges, functions/RPCs/triggers/policies/types and data together. Roles are a separate password-free catalog, not transaction-consistent with the dump; freeze role/config changes during scheduled/pre-deployment capture. `realtime` runtime and Vault intentionally excluded. Catalog preflight refuses additional persistent schemas, nonempty Vault, or external-job/encryption extensions until scope/containment is reviewed. Scope can grow without redesign: add schema/asset coverage and revalidate it before using new state.

`--schema` archives do not automatically include all dependency objects or cluster settings; extension versions, managed roles, Auth/Storage versions and project settings need a compatible baseline. No universal one-command clone is claimed. A full archive is retained; new-project restoration needs a reviewed subset for platform-managed objects. [pg_dump semantics](https://www.postgresql.org/docs/17/app-pgdump.html).

Writer checks every pipeline exit status, nonzero ciphertext, creates timestamp+random bundle names without overwriting, writes manifest/SHA-256 and removes only its own partial ciphertext on failure. No plaintext dump is written; credentials are not arguments. Successful writer output means **local export only**, not offsite protection. Manifest explicitly starts `archive_validated=false`, `restore_tested=false`.

Verification checks both sizes/checksums, age authentication/decryption, pg_restore TOC and full archive decoding without executing SQL; output discarded. Store verification receipts separately with run ID and timestamps. Upload all files+manifest to immutable timestamp prefix, re-download and compare hashes, then write final remote-success receipt. Checksums detect damage; age provides authenticated encryption, but neither proves database correctness. Bucket permissions/immutability protect manifests/receipts. [age tooling](https://github.com/FiloSottile/age).

For low-load hourly exports, measure duration/storage/load; alert if the job cannot finish within its schedule. Never overlap dumps or loosen correctness checks to make a green status. A future dedicated dump role needs proven complete Auth/RLS/bypass/catalog permissions; use controlled server-side access initially, never clinic service/browser sessions.

Hourly export RPO includes snapshot-to-remote completion lag; measure it and schedule more frequently if required to meet the ≤1-hour disaster target. ## Common restore controls and validation

Recovery lead opens incident with timestamp/scope and a second Apero approver. Contain writes/intake using existing downtime/telephony procedures; record in-flight calls/requests and stop deploys. Preserve safe error evidence and last-good release hashes. Do not delete the damaged database. If safe, capture a separate encrypted forensic snapshot without calling it a good backup. Never enable a restored environment's outbound SMTP/webhooks/carrier or background tasks before isolation is verified.

Select last known-good point **before the earliest bad write**, not merely newest file. Record UTC time, checksum, backup window and expected loss. Download into restricted encrypted host; verify hashes/decryption/archive and approved provenance. Restore first into isolated compatible Supabase/local stack with production network egress blocked and no production provider secrets. Prefer managed clone only if supported/approved and external jobs cannot escape. No second paid production stack was created by this task.

Restore engine procedure for a disposable compatible baseline:

1. Review decrypted TOC on the encrypted isolated host (`age -d … | pg_restore --list`); TOC can contain object names, restrict its output. Full archive verification command above emits no content. Match PostgreSQL/Auth/Storage/extensions versions.
2. Review role SQL in restricted memory/encrypted workspace; create only missing application roles/password-free attributes and required grants. Never blindly apply exported Supabase internal role ownership/admin grants to another hosted project. Reset custom LOGIN passwords separately.
3. Reconcile built-in Auth/Storage schemas already present with the archive. Prepare a reviewed TOC for schema objects versus managed baseline/data; preserve custom policies/functions/ACLs. Reconcile actual migration history, rather than applying all migrations on top of a restored current schema.
4. On an **empty disposable database only**, a full archive restore can use `age -d -i "$RECOVERY_IDENTITY" "$ARCHIVE" | pg_restore --exit-on-error --single-transaction --dbname "$DISPOSABLE_DATABASE"` with libpq host/user/pgpass pointing exclusively to the isolated environment. Enable shell `pipefail`; never put a credential URL in `--dbname`. Existing hosted baseline requires a validated TOC (`--use-list`) instead. No `--clean` or production host in this runbook command. Restricted error handling must prevent SQL/patient values escaping logs.
5. If dependencies/ownership/platform objects collide, stop. Use the Supabase-supported schema/data/role migration workflow and explicitly preserve Auth/Storage customizations/history, with platform support where required; never ignore restore errors globally. This exact managed-platform mapping remains an outstanding drill requirement. [Supabase logical migration procedure](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).
6. Validate aggregate counts against backup snapshot manifests/test baselines, table/column/type/index/function/trigger/policy/grant inventories, extensions/history; orphan checks; unique/exclusion constraints and RLS per role and two clinics; Auth IDs/profile membership, password login/MFA/redirects/email flows on controlled accounts; booking availability/book/reschedule/cancel/idempotency and existing requests using synthetic data **only inside isolation**. Check data loss interval against authorized clinic records without logging values. No paid Retell calls.
7. Reject any unexpected cross-clinic access, missing Auth account/function, restore error, broken relationship, revived checked slot/lease, duplicate booking risk, or mismatch that is not explained and signed off. Never replay cached booking requests or all historical webhooks to fill a gap.
8. Approvers accept validation and known loss; freeze writes again, take a final safe checkpoint, prepare explicit cutover+rollback plan and update URLs/keys/bindings consistently. Revoke sessions/rotate compromised secrets as appropriate. Check dashboard, unsigned-denial probes, synthetic tools in isolation, staff access, schedules, Open Requests, current bookings and webhooks. Obtain clinic reconciliation for gaps. Reopen intake only after acceptance; monitor two clean five-minute windows using existing monitoring runbook. Remove disposable recovered patient copies and revoke temporary credentials after closure.
