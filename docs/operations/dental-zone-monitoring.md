# Dental Zone launch: production errors and system logs

Use the existing Supabase project `svoybvzvmygszklcmudh`. No monitoring vendor, database log table, log drain, queue, notification integration or paid call was added. This is temporary **manual monitoring**, not automatic notification or 24/7 coverage.

1. **Existing infrastructure.** Supabase stores function console logs, function invocations, API gateway, PostgREST, PostgreSQL and Auth logs/audit events. Existing `voice_operations`, `voice_call_state` and `voice_requests` are operational state and staff follow-up records, not a second error warehouse. Booking/calendar/system fallbacks already had safe fixed categories, but inconsistent metadata. Lovable runtime hooks and server exception capture existed; no monitoring SDK, application alert job, pg_cron or pg_net extension was found. Local uncommitted performance instrumentation was inspected but is absent from deployed source and was excluded from this release.
2. **Missing/unsafe.** Raw exception messages, stacks and cause chains were expanded in the server console and forwarded by the React boundary to optional Lovable hooks. Errors can contain patient data or credentials. Database error codes were arbitrary strings. Webhook exceptions and several security/recording-access denials lacked explicit event categories. Console failures could interrupt fallback handling. Successful webhooks were logged on every delivery.
3. **Changes.** An allowlist-based JSON logger replaces those application logs. Function boundaries record HTTP 5xx, 401/403, recording 404 and unexpected exceptions. Existing JSON fallback helpers retain their patient behavior and log their failures even when returning HTTP 200. Human/unknown-answer saves and transfer state changes are the only routine success events retained, because they confirm important handoffs. Normal requests, availability successes, confirmed bookings and completed webhooks stay quiet. A shared database event may accompany the request's failure event; count request/call identities rather than treating each line as a separate incident. There are no retries, database writes for logging or cross-request global clinic contexts.
4. **Events.** `booking_failed`, `calendar_unavailable`, `unknown_answer_followup_failed`, `human_escalation_failed`, `transfer_failed`, `recording_access_failed`, `webhook_failed`, `authentication_failed`, `authorization_denied`, `system_unavailable`, `database_error`, `internal_error`. Dependency categories include `provider_error`, `database_error`, timeout, invalid response and fixed configuration/backend/integration unavailability labels. Webhook failures cover call-processing persistence and transfer-event processing. Important success events: `human_escalation_saved`, `unknown_answer_saved`, `transfer_state`.
5. **Exact application metadata.** Every event has UTC ISO `timestamp`, allowlisted `category`, `component`, and `state` (`success`/`failure`). Optional fields: UUID `clinic_id`, `request_id`, `conversation_id`, `follow_up_request_id`; bounded Retell `call_id` beginning `call_`; allowlisted `dependency_category`, booking `reason`, `transfer_result`; booleans `follow_up_saved`, `transfer_attempted`, `fallback_escalation_saved`, `fallback_response_returned`; integer HTTP `status` (400–599); five-character SQLSTATE `database_code`. Missing/invalid identifiers are omitted. Boundaries generate their own UUID request IDs; caller request headers are not copied. Helpers generally correlate by clinic/call rather than request UUID. Database utility events may have no clinic when the utility is not given trusted context. No arbitrary operation name or user ID is logged.
6. **Exact exclusions.** Access/refresh tokens, API keys, service-role credentials, Retell secrets, authorization headers and other headers; passwords; raw request/webhook bodies; transcripts; recordings and recording URLs (including signed URLs); patient names/phones; appointment payloads and slot tokens; raw provider/database responses; free-text errors/messages/stacks/causes; route URLs/query strings; free-text escalation reasons/questions; environment values. Unknown metadata keys are dropped rather than recursively redacted. Optional Lovable hooks get only a generic error without stack or route/context, and hook failures are swallowed.
7. **Production access.** Open [Supabase logs](https://supabase.com/dashboard/project/svoybvzvmygszklcmudh/logs), choose Edge Function, and use a 15-minute window. Or open [Edge Functions](https://supabase.com/dashboard/project/svoybvzvmygszklcmudh/functions), select a function, and inspect **Logs** (console events) and **Invocations** (HTTP results, runtime/bootstrap failures). Filter by the category string, clinic UUID, call ID or request UUID. Use [Logs Explorer](https://supabase.com/dashboard/project/svoybvzvmygszklcmudh/logs-explorer) for the queries below. Select Auth/Auth Audit, Postgres and API gateway in the project log view for direct browser Auth/RLS/database failures that bypass Edge code. Portal server errors use the existing deployment console/runtime logs; browser exceptions appear in the browser console or the available Lovable hook. There is no new persistent browser error collector. The public frontend must be published through Lovable for its new sanitization to take effect; backend deployment does not publish frontend assets.
8. **Alerts.** No reusable application alert/notification mechanism was found. Log-drain listing returned HTTP 403 with the available management credential, so account-level drains and external alert rules could not be verified. We did not configure any automated alert. Check Project Settings → Log Drains with an Owner account before assuming an existing drain is absent. Existing logs are enough for a *staffed* clinic #1 launch; logs alone never notify an unattended operator.
9. **Manual launch procedure.** Assign a named Apero technical operator and a backup before taking real calls. Verify both can open project logs and the clinic's Open Requests. At opening, inspect the last hour, then keep the log view open and refresh **every 5 minutes** while clinic #1 is taking calls; at closing inspect the entire day. Use the two queries below, and inspect Auth, Postgres/PostgREST and Open Requests at least every 15 minutes and whenever an incident appears. If the log view is empty, check that the function invocation timestamps are current: no logs does not prove health. If Supabase/log delivery is unavailable, use [Supabase status](https://status.supabase.com/) and the existing clinic direct-contact fallback; do not infer health from missing application events.

   Act immediately on any genuine booking creation failure, webhook/call-persistence failure, database outage, or unsaved escalation/request. Treat **3 distinct failed requests/calls in 5 minutes**, or **two consecutive failing 5-minute checks**, as a sustained backend/system-unavailable incident. Inspect individual invocation 5xx even without a console event. For calendar, recording and transfer failures, investigate the first occurrence and involve the technical operator if it repeats on two distinct calls/requests within 15 minutes. Review authentication/authorization bursts of **5 denials in 5 minutes** and any unexpected denial from clinic staff; distinguish expired sessions or invalid signatures from infrastructure failure using Auth/invocation logs. These are manual launch thresholds, not automated rules.

   Record only time/window, category, component, clinic/call/request IDs, count and safe dependency/SQLSTATE in the existing incident notes. Investigate the corresponding patient/call in the authorized dashboard only when needed. Check whether a follow-up actually saved; clinic staff must handle Open Requests. A failed or interrupted booking is never permission to retry creation: check existing appointments and call state before any staff action. During a sustained outage, stop accepting automated bookings using the existing operational downtime procedure and direct patients to the clinic. Verify recovery with dashboard availability and safe unsigned/synthetic backend probes; a real paid Retell call needs separate authorization. Close the incident only after two clean 5-minute checks and review of affected Open Requests.
10. **Tests.** Run `npm run test:monitoring`, the booking/calendar/human/unknown/transfer/system fallback tests, `node retell/master/tests/edge-isolation.test.mjs`, recording access, clinic-user/team/auth/conflict suites, flow contracts, `npm run typecheck:clinic-users-edge`, and `npm run build`. The deployment evidence records exact results. Tests cover strict metadata rejection, poisoned messages/tokens/transcripts/provider payloads, real signed webhook failure, actual recording factory denials/provider access, silent normal success, unchanged fallback/permission behavior and throwing console/reporting hooks. Provider bundling precedes deployment.
11. **Deployment.** See `dental-zone-monitoring-release.json` for active versions, probes and source publication. All affected functions preserve existing JWT settings. The older production availability body reader was preserved in that function's deployment bundle; only its logging changed. No database migration, Retell flow change or paid call is required.
12. **Launch conditions/limitations.** Assign the manual monitoring operator/backup and publish the frontend sanitization before the full logging-safety change is live. Log availability/delivery and retention are controlled by the existing Supabase plan. Native platform logs may contain IPs, request URLs, query filters, Auth identities and SQL detail; the application logger cannot sanitize provider-managed fields. Keep platform log access limited to technical operators, use the safe projection queries below and do not export raw logs into public tickets. Source logs and all currently retained accessible platform sources were searched for credential/patient-content patterns; none matched actual token/value patterns, but regex checks do not prove all historical data safe. Some gateway messages mention transcript/name *column selections*, not dumped contents. Provider-managed gateway metadata also includes partial API-key prefixes: 153 retained entries matched those prefixes; none matched a full secret/bearer-token pattern. These provider fields cannot be sanitized by our application logger and must not be copied into incident exports. Lovable-host console logs could not be retrieved through a connected deployment API, so historical portal logs were not audited. Public frontend publication and manual coverage remain operational requirements. Existing live transfer remains subject to its separate configuration/real-phone acceptance requirements; this release does not activate it.
13. **After launch.** Automated threshold notifications, proactive external health probes, a privacy-safe persistent browser collector, longer retention, aggregate dashboards and log drains can wait until real volume and staffed coverage justify them. Do not add a paid vendor solely for clinic #1.

The current project's log tool uses ClickHouse's unified `logs` source. These aggregate queries were executed successfully against production. In the dashboard use **Explorer**, not the database SQL Editor.

```sql
-- Safe application failures, including HTTP 200 fallbacks.
select
  JSONExtractString(event_message, 'category') as category,
  JSONExtractString(event_message, 'component') as component,
  count(*) as events,
  uniqExactIf(JSONExtractString(event_message, 'call_id'),
              JSONExtractString(event_message, 'call_id') != '') as distinct_calls,
  uniqExactIf(JSONExtractString(event_message, 'request_id'),
              JSONExtractString(event_message, 'request_id') != '') as distinct_requests
from logs
where source = 'function_logs'
  and timestamp > now() - interval 5 minute
  and JSONExtractString(event_message, 'state') = 'failure'
group by category, component
order by events desc;
```

```sql
-- Runtime/gateway failures: catches import errors, timeouts or unreachable DB
-- when our logger never executes. Also sees direct browser Auth/API denials.
select source, log_attributes['response.status_code'] as status, count(*) as events
from logs
where timestamp > now() - interval 5 minute
  and source in ('function_edge_logs', 'edge_logs')
  and toInt32OrZero(log_attributes['response.status_code']) >= 400
group by source, status
order by source, status;
```

For safe incident detail, select only `timestamp`, JSON category/component/clinic/call/request IDs and dependency category from `function_logs` where category matches. Do not select `*` or unfiltered native `event_message` into shared incident exports. Increase the window to 15 minutes for important failures. Filter `JSONExtractString(event_message, 'clinic_id')` by the actual clinic UUID when helpful, but always review unscoped failures too: startup or authentication failures often have no clinic.
